# Updating an existing installation

This release adds daily-plan revisions, acknowledgement versions, named break cover, one-day duration exceptions and per-agent Slack delivery records. Back up the database before updating an existing installation. Do not reset schedules or use a destructive schema-push flag to complete an upgrade.

## Existing databases from the earlier release

1. Build the new image before the maintenance window: `docker compose build app`.
2. Stop the application so posting and acknowledgement writes cannot run during the change: `docker compose stop app`. Keep PostgreSQL running.
3. Take a full PostgreSQL backup and verify that it can be restored. Keep the existing environment file and encryption/session secret securely; changing that secret can make saved Slack credentials unreadable.
4. Apply `prisma/patches/20261014-plan-repairs.sql` once, using a database administrator connection and stopping on the first SQL error. The patch retains existing records and adds the new fields, tables and indexes. Do not run it again on a database where these changes already exist.
5. Restart the rebuilt application: `docker compose up -d --no-build app`.
6. Check application health, sign-in, saved settings, roster views and exports. Preview a Slack briefing before testing real delivery. Confirm there is only one production instance running the posting scheduler and Socket Mode listener.

For the included Compose database, a Linux shell can apply the patch with:

```sh
docker compose exec -T database psql -U tradeling -d tradeling_cs_operations -v ON_ERROR_STOP=1 < prisma/patches/20261014-plan-repairs.sql
```

Use the actual database/user names if your deployment differs. This command does not create a backup; complete step 3 first. Backups, environment files, credentials and restored test databases must never be committed to the repository.

If the earlier plan-repairs patch was already applied in a test installation without the duration-exception column, apply only `prisma/patches/20261014-break-duration-exception.sql`. It adds the missing column without reapplying the rest of the patch.

## New installations

Follow the README setup steps against an empty PostgreSQL database. The first startup creates the schema and initial defaults. Later startups keep existing operation configuration instead of restoring removed business defaults. Set a private, unpredictable session secret of at least 32 characters; production no longer accepts the fallback secret. Replace demo credentials and use HTTPS before broader use.

## Behaviour to check after upgrading

- Existing acknowledgement records start at plan revision 1. A changed or rebuilt plan gets a new revision; old-message acknowledgements do not apply to it. Repeated clicks on the same version retain the first acknowledgement time.
- Prepared plans are checked against their operation configuration before posting. Review and rebuild stale future plans rather than bypassing the check.
- Manual break-duration exceptions apply to one agent/date only. Shift boundaries, spacing and cover checks still apply. Regenerated breaks use normal settings.
- Fairness uses recorded history across months and years. Existing confirmed history is preserved; future generation still needs review when staffing or leave changes.
- Mobile navigation and deployment-specific security work were not part of this repair. Accepted imported October coverage exceptions do not gain a new approval bypass in this release.

Run `npm run test:core` and `npm run lint` with development dependencies installed. Production weekly checks use `npm run audit:week -- YYYY-MM-DD`, choosing the configured start of a complete scheduling week. The audit reports recorded duration/rest exceptions rather than treating them as silent rule changes. No audit command sends Slack messages.
