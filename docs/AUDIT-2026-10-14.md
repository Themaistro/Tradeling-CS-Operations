# CS Operations audit — 14 October 2026

This records the original read-only review of the application source, deployment configuration, selected live cloud data, and isolated test scenarios. No production schedules were regenerated, no Slack messages were sent, and no operational settings were changed during that review. The findings below describe the application at the time of the audit, before the repair pass.

## Repair status

The subsequent repair pass implements task saving and interval checks, planned-leave reconciliation, protected past schedules, first-install-only seeding, main-break cover checks, plan-version acknowledgements, retained rest warnings, language checks, historical shift-time protection, stale-plan detection, Slack delivery claims and private-message retry records. Daily Tasks also supports explicit one-day break-duration exceptions without changing the normal policy. Core tests, build checks and isolated three-month scheduling tests passed.

See [the fairness test](FAIRNESS-TEST-2026-10-14.md), [fairness behaviour](SCHEDULING-FAIRNESS.md) and [upgrade steps](UPGRADE-2026-10-14.md). These tests do not establish exhaustive security or larger-team validation. Mobile work was excluded; existing short-break flexibility was retained. The accepted pre-cutover October approval exception was left out of scope at the user's request. Live deployment is a separate step.

## Evidence and limits

- The live container is healthy, with zero restarts reported at the time of inspection.
- The existing weekly audit passed for 19–25 October: six active employees, 42 roster entries, 30 working assignments, 102 task assignments, and 60 breaks.
- The earlier live Calls audit checked 18 prepared days, 77 working agent-days, and 162 account coverage windows with no missing Calls coverage.
- Six isolated scheduling simulations covered October, November, and December with Sunday- and Monday-start weeks. The tested six-agent configuration had no weekly-limit or consecutive-work-limit violations, and no critical coverage warnings.
- Isolated route tests reproduced the manual-task, out-of-shift-task, planned-leave, and weak break-cover checks described below. They used mocked persistence, not production writes.
- Dependency audit: five package entries flagged, tracing to two distinct advisories. Package-chain entries are not five independent exploits.
- This was not a penetration test or an exhaustive graphical browser walkthrough. Slack message history is unavailable to the current bot because the required scope is missing. Delivery and visual rendering of a new Slack post were not retested by sending messages.
- Passing the existing weekly audit is useful but does not establish that all operation rules are enforced. Several findings below expose checks it does not perform.

## Findings requiring repair

### 1. Manual task creation is broken from the current form — High, reproduced

The Daily Tasks form sends date, employee, task, note, and priority, but no start/end fields. The task API compares missing times as empty strings; `"" >= ""` evaluates to true, so the form's normal request is rejected with “Provide a valid task start and end time.”

Evidence: `src/app/(dashboard)/tasks/page.tsx`, function `addTask`; `src/app/api/daily/tasks/route.ts`, `POST`. An isolated form-equivalent request returned HTTP 400.

Repair: either supply valid editable/default task times in the form or derive the permitted window on the server. Ensure changing a note does not erase an existing task's times.

### 2. Planned leave cannot be added once a roster exists — High, reproduced

The Team API rejects planned leave whenever an assignment exists for that date, regardless of whether the schedule is approved or draft. Its instruction to reopen and regenerate first does not resolve the problem: regeneration creates another assignment, and saving leave remains blocked. Removing or changing existing planned leave is affected too.

Evidence: `src/app/api/team/[id]/route.ts`, `plannedImpactDates`/`impacted` checks. The isolated request with an impacted DRAFT period still returned HTTP 409.

Repair: let planned leave be saved through an explicit review flow that marks affected future schedules for adjustment. Allow draft schedules to reconcile the change; keep past history protected.

### 3. Regeneration replaces past operational history — High, code-confirmed

After reopening a current month, generation deletes all task assignments, breaks, and shift assignments for that month and starts at month start once the one-time transition is complete. Past-history input reads dates before generation start; it does not preserve the already-worked dates inside the regenerated month.

Evidence: `src/app/api/schedule/route.ts`, `scheduleStart`, and the three month-wide deletes in `POST`.

Repair: preserve completed dates and regenerate from a clearly displayed effective date. Include preserved days when calculating continuity and weekly limits.

### 4. Startup seeding restores removed operation configuration — High, code-confirmed

The application executes the seed on every container start. The seed unconditionally ensures default accounts by code, default task names, default operating and coverage windows, and every active employee's capabilities for the default accounts. Renaming an account code/task or removing service windows/capabilities can therefore lead to defaults being recreated at the next restart. The recent shift correction prevents one duplicate-shift path but does not solve the wider bootstrap issue.

Evidence: `Dockerfile` startup command and `prisma/seed.mjs` account/task/window/capability upserts.

Repair: separate first-install defaults from normal startup. Use explicit migrations for legacy data instead of reapplying business defaults on every restart.

### 5. Break safety does not establish task-specific cover — High, reproduced structurally

Both generated and manually edited breaks only require another person to be working and not on break. They do not check account qualification, required language cover, chat ownership, or whether the proposed cover can leave their focus responsibility. No named chat-break handover is recorded.

Evidence: `findSlot` in `src/app/api/daily/plan/route.ts` and `hasCoverage` in `src/app/api/daily/breaks/route.ts`. The isolated break request succeeded with only a generic second worker; no qualification/task data was queried.

Repair: validate the live channels and language/account requirements throughout the break, and record an explicit cover when needed. Do not apply focus-task exclusivity to the sole evening agent, who intentionally owns all Hugo Boss queues.

### 6. Task times can be outside shift and account hours — High, reproduced

The task API checks that the employee's shift overlaps the account at some point but does not constrain the submitted task times to the shift/account windows. A 20:00–21:00 task was accepted for a 09:00–18:00 worker and account in the isolated test.

Evidence: `src/app/api/daily/tasks/route.ts`.

Repair: validate the complete submitted task interval, not merely overlap between the shift and account.

### 7. Rebuilding a daily plan retains its old acknowledgements — Medium, code-confirmed

Plan replacement deletes tasks and breaks but leaves acknowledgement rows keyed by agent/task/date. The same categories can consequently appear acknowledged even after responsibility or timing changes. An old Slack button also acknowledges the current database tasks for its date rather than a version of the message the person actually read.

Evidence: transaction at the end of `src/app/api/daily/plan/route.ts`; acknowledgement handler in `server.js`; Overview's category-based acknowledgement check.

Repair: version daily plans and associate acknowledgement with the posted version. Preserve the first timestamp for repeat clicks on the same unchanged version.

### 8. Rest-pattern warnings are lost after generation — Medium, code-confirmed

The engine emits `REST_PATTERN_OVERRIDE`, but the schedule page only retains the number of generation warnings and immediately reloads the period. The GET route rebuilds staffing/replacement warnings, not rest-pattern warnings. A reviewer cannot reliably see which agent's planned rest was affected after reload.

Evidence: `generate-schedule.ts`, `SchedulePage.generate`, and `GET /api/schedule`.

Repair: persist/recalculate rule exceptions and show them in the review panel. Keep accepted coverage exceptions available for later review.

### 9. Bilingual account requirements are not enforced consistently — Medium, code-confirmed

Schedule GET reports account-level bilingual shortages. Approval checks account headcount but omits account-level `minimumBilingual`, unless a separate shift override also enforces it. Overview calculates coverage from headcount alone, so it can show all targets met despite a language shortfall.

Evidence: `src/app/api/schedule/route.ts`, GET versus PATCH; `src/app/(dashboard)/overview/page.tsx`, `coverageChecks`.

Repair: share one validation function between generation review, approval, and Overview.

### 10. Shift time edits rewrite the meaning of existing schedules — Medium, code-confirmed

Assignments store a shift ID, not a snapshot of its times. Changing that shift's times immediately changes historical and approved schedule displays while task and break times remain as originally saved. Shift deactivation also does not reconcile existing future assignments.

Evidence: `ShiftAssignment` schema; `src/app/api/shifts/[id]/route.ts`; schedule/export queries include the current related shift.

Repair: distinguish a safe label change from an effective-dated timing change. Review affected future plans and preserve historical timings.

### 11. Config changes can leave prepared plans stale — Medium, code-confirmed

Changing account hours, task method/priority, eligibility, or task availability does not invalidate/reconcile existing daily plans. The planner and automation treat any existing tasks OR breaks as `PLAN_EXISTS`, so a partially prepared or stale day can proceed to posting. Account labels embedded in generated note strings remain old after an account rename.

Evidence: operation/task update routes; `PLAN_EXISTS` check; generated task `note` strings; Slack post queries do not filter category/account active state.

Repair: track the operation configuration version used by a plan, validate completeness before posting, and offer a controlled future-plan refresh.

### 12. Short-break rules differ between generation and manual editing — Medium, code-confirmed

Generation can move a short break earlier than the configured delay to protect coverage, with a warning. Manual saving rejects that same interval. The planner can also attempt a short break after failing to find a main break, while manual editing requires a main break first.

Evidence: `findSlot` fallback in `daily/plan`; `otherBreak` and delay checks in `daily/breaks`.

Repair: use a shared break validator and explicit exception handling. Keep a consistent rule for skipped/disabled main breaks.

### 13. Break labels remain hardcoded — Medium, code-confirmed

Daily Tasks displays `40m`/`20m` and “Main · 40 min”/“Short · 20 min” even when settings change break durations. The API uses settings, making the interface contradict its own validation.

Evidence: `src/app/(dashboard)/tasks/page.tsx`, break badges and type options.

Repair: display actual saved duration on badges and configured duration in the form.

### 14. Mobile navigation is missing — Medium, code-confirmed

The sidebar and sign-out control are hidden below the large-screen breakpoint, with no alternative navigation menu in AppShell. Smaller-screen users cannot access the normal section links through the shell.

Evidence: `src/components/layout/app-shell.tsx`, `hidden ... lg:flex` sidebar.

Repair: add a mobile menu with the same navigation and sign-out action.

### 15. Settings validation accepts invalid clocks/timezones — Medium, code-confirmed

Several APIs only require `NN:NN`, so values such as `25:99` can pass format checks. Settings accepts an arbitrary timezone string; an invalid value can break date rendering, Overview, and automation. JSON/date error handling is also inconsistent across routes.

Repair: centralize actual clock ranges, valid dates, timezone validation, and structured API errors.

### 16. Some configuration remains overridden or name-dependent — Medium, code-confirmed

Focus generation writes priority 1 regardless of its configurable default priority. Shared queues are merged by normalized task name; the first category determines method/priority, so different account settings for equally named tasks are not reconciled. Evening-message classification uses the latest task start time; an unrelated later support task can change the evening heading. The live audit script identifies night work by the name matching Late/Night.

Repair: honor or explicitly restrict focus priority in the UI; reconcile shared-queue configuration; derive service transitions from structured account windows; remove shift-name dependence from audits. These are targeted configuration-consistency changes, not a request to redesign the entire engine.

### 17. Duplicate-post protection is not atomic — Medium, code-confirmed

Automation checks for a SENT log before posting, then inserts the log after Slack accepts the message. There is no database claim/unique delivery key. Two app instances or overlapping manual/automatic requests can both send before either records success. A log-write failure after successful delivery is reported as a failed post, inviting a retry.

Evidence: `server.js` and `src/app/api/slack/post/route.ts`.

Repair: claim a delivery attempt atomically and distinguish external delivery from bookkeeping failure. Retain intentional manual resend as an explicit action.

### 18. Private-message delivery failures are not retained — Medium, code-confirmed

The post log records the channel post only. Private-message failures/skips are returned to the caller, but not stored. The automatic runner only handles non-OK HTTP responses; a successful channel post with failed DMs returns OK, so managers lack a persistent delivery/retry record.

Repair: retain per-agent delivery status and support retrying only failed personal briefings.

## Other constraints and lower-priority items

- Automation deliberately posts only during the configured minute. Downtime or failure in that minute results in a missed post; there is no bounded retry/manager notification. This follows the previously requested no-late-post behavior and should not be changed without an explicit retry policy.
- Slack sections are not split by length. Large teams can exceed Slack message limits; larger-team support needs batching and load testing. This was not reproduced by posting a large message.
- Grouped Slack task notes use only the first assignment's note, potentially hiding other agents' custom notes. Account labels are mixed with optional notes; disabling notes also hides account context.
- Login lacks rate limiting; deployment defaults allow weak credentials and a predictable session secret if configuration is omitted. The current HTTP demo requires separate production hardening. The known admin/password decision was not changed in this audit.
- Environment Slack tokens override saved Settings tokens. This is supported behavior, but the UI should show which source is active. Removing saved tokens does not disconnect an already-running Socket Mode client until restart.
- “System ready” is a static green label, not a health/readiness check.
- Schedule reset deletes opening history but retains rotation baselines and planned time-off. The reset scope should make that distinction explicit.
- JSON export is an export, not a complete tested restore mechanism. Database backups and a restore exercise remain separate deployment work.
- `scheduleBuildCutoff` is used as a planning-reminder label; there is no automatic generation job on that day. `splitDate`/`generationScope` remain schema fields without an implemented generation workflow.

## Dependency review

`npm audit --omit=dev` reported three high package entries (`deepmerge-ts`, `@prisma/config`, `prisma`) and two moderate entries (`uuid`, `exceljs`). These trace to two advisories:

- [DeepmergeTS recursive-graph stack exhaustion](https://github.com/advisories/GHSA-ggr8-5vv4-36mx). This requires recursive object graphs; ordinary JSON alone does not create that condition. An exploitable unauthenticated web path was not established in this audit.
- [UUID buffer bounds issue](https://github.com/advisories/GHSA-w5hq-g745-h8pq). The affected transitive dependency comes through ExcelJS. Reachability through this application's export usage was not established.

Do not run a force upgrade/downgrade based solely on the suggested automated fix. Review compatible dependency updates and test exports and Prisma tooling.

## Recommended repair order

1. Repair manual task creation, task time boundaries, and planned-leave reconciliation.
2. Separate startup bootstrapping from persistent configuration; freeze past schedule data.
3. Share live-cover/break validation; retain schedule warnings and language checks.
4. Add plan versions for acknowledgement and config changes.
5. Make Slack delivery reliable and auditable, then finish mobile/dynamic-label refinements.
6. Complete deployment security, compatible dependency remediation, backup/restore verification, and larger-team load tests before broader production use.

This audit supports a focused repair pass. It does not justify replacing the working scheduling engine or hardcoding account names, weekdays, or staffing counts.
